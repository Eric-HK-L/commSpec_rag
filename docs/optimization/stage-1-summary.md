# 阶段性总结 — 检索质量优化（Stage 1）

> 时间跨度：一次会话内的完整优化迭代。所有结论以实测评测数据为准，负面结果如实记录。

## 0. 关键约束与背景

- **知识库当前只含 36/38 系 + O-RAN**（65,991 chunks），缺 23/24/22/21 系核心网/UE 规范。
  - 用户明确"暂时不需要核心网"，这是既定约束，非待办。
- 评测集原 70 题中 32 道是核心网题（当前库永远答不了），已重设计为 **40 题 L1/L2 聚焦**（含 10 道多协议交叉题）。

## 1. 已验证收益（保留）

| 优化                                   | 效果                                   | commit    |
| -------------------------------------- | -------------------------------------- | --------- |
| BM25 域名感知分词                      | RAN 重排 Recall@5 +6.1%（0.706→0.768） | `7e8d502` |
| top-k spec 多样性重排                  | RAN +7.9%（0.768→0.846）               | `ef79ef2` |
| 跨协议题更激进多样性（max_per_spec=1） | 多跳 R@5 +0.20（0.70→0.90）            | `4366995` |
| 多跳触发改为 query 跨协议信号          | 确定性触发（10/10 命中、0 误触发）     | `33e2081` |
| 多跳缺口分析输入增强                   | 10 条×150字符+section标题              | `33e2081` |

**核心机制洞察**：多跳题的 expected spec 大多**已在候选池**，瓶颈不是"召回不到"而是"排序挤不进 top-5"——所以排序侧（多样性）比召回侧（多跳子查询）更有效。

## 2. 已验证负面（排除/回滚）

| 实验                             | 结果             | 结论                                        |
| -------------------------------- | ---------------- | ------------------------------------------- |
| nprobe 32→128                    | 无变化           | ANN 索引不是瓶颈                            |
| RRF k 扫描（dense/sparse 加权）  | 无收益           | reranker 抹平差异，默认 60/60 最优          |
| 36 系权威 boost 拓宽             | -2.6%            | LTE 召回失败是池外漏召非排序，boost 无效    |
| embedding_text 编入 section_path | **-9.2%**        | 层级路径稀释正文 dense 信号（domain shift） |
| reranker max_length 2048         | -5.8%            | 长序列注意力稀释，1024 最优                 |
| 表格拆小（table_max_chars 2000） | **-4.6%**（R@5） | 见下                                        |

**重要负面发现（表格语义单元化）**：把大表拆成行组（2000 字符）反而让 R@5 下降 0.046。
3GPP 参数表是"列举型"（如 PRACH preamble formats 表），整表 chunk 的 dense 向量能整体覆盖
"有哪些 format"这类查询；拆成行组后每个行组只覆盖部分、候选池被稀释。**"小 chunk 更好"的
常见假设对协议参数表不成立**，已回滚 table_max_chars=5000。

## 4. 当前基线（新题库 40 题）

| 指标          | 值           | 说明                             |
| ------------- | ------------ | -------------------------------- |
| 全部 Recall@5 | ~0.89        | 波动 0.87~0.91（LLM 噪声 ±0.05） |
| 单步 R@5      | ~~0.87~~0.92 | 30 题                            |
| 多跳 R@5      | ~~0.90~~0.97 | 10 题（跨协议交叉）              |
| 初检 R@5      | ~0.65        | reranker 仍是强力兜底            |

**LLM 噪声问题**：评测的 query expansion + 多跳缺口分析依赖 LLM（temperature 0.3），
单次评测有 ±0.05 噪声，A/B 需以多次平均或"机制确定性"辅助判断。

## 6. 关键方法论教训

1. **先定位瓶颈再动手**：初检 vs 重排 Recall 的拆分，快速定位了"排序 vs 召回"的瓶颈，
   避免了在错误方向（nprobe、权威 boost）上浪费。
2. **配置覆盖陷阱**：`.env` 的 `INGESTION__TABLE_MAX_CHARS` 覆盖代码默认值，导致一次 68 分钟
   重摄入实际未生效。重摄入/评测前必须验证 `build_splitter()` 实际生效的配置。
3. **负结果同样有价值**：nprobe/RRF/path_text/表格拆小 等 6 项负面实验，明确划掉了无效方向，
   避免后续重复投入。
