## 0. 指导原则（来自 Stage 1 教训）

1. **先有可靠标尺，再做优化**：Stage 1 的 LLM 噪声（±0.05）严重干扰 A/B 判断，必须先升级评测。
2. **拆分类优化要谨慎**：表格拆小（2000）实测 R@5 -4.6%，证明"小 chunk 更好"对 3GPP 列举型
   参数表不成立。公式/图表的任何"拆分/注入"都要实测验证，不预设方向。
3. **配置覆盖陷阱**：重嵌入前必须验证 `build_splitter()` 实际生效的配置（`.env` 会覆盖代码默认值）。
4. **负结果也是交付**：明确划掉无效方向，避免后续重复投入。

## 1. P0 — 评测升级（先做，这是标尺）

### 1.1 章节级 Recall（当前只按 spec 整篇算，高估答案质量）

**现状**：`tests/eval/metrics.py` 的 Recall 只匹配 `expected_specs`（整篇文档），不校验章节。
"正确 spec 进了 top-5" ≠ "正确章节进了 top-5"，真实答案质量被高估。

**方案**：

1. `metrics.py` 新增章节级判定：命中结果需同时满足 `spec_number` 匹配 + `section_number`
   前缀匹配 `expected_sections`（如期望 "6.3.3"，命中 "6.3.3.1" 算命中）。
2. 为 `test_set.json` 的 40 题补齐/校正 `expected_sections`（需对照各 spec 的章节结构核对）。
3. 输出两套指标：spec 级 Recall（现状）与 section 级 Recall（新增），后者作为主指标。

**成本**：低（纯评测代码 + 题库校正，无重嵌入）。
**收益**：让后续所有优化有可信标尺，避免"spec 命中但答案不对"的假阳性。

### 1.2 LLM 噪声控制

**现状**：评测的 query expansion（temperature 0）相对确定，但多跳缺口分析（temperature 0.3）
有噪声；单次评测 ±0.05，导致小增益（如 +0.03）不可判。

**方案**（按成本从低到高）：

1. 多跳缺口分析 temperature 0.3 → 0（`multi_hop.py` 两处 `chat(..., temperature=0.3)`）。
2. 评测支持 `--repeat N` 多次运行取均值（需注意每次 ~10 分钟）。
3. 若 LLM API 支持 seed 参数，固定 seed 使 query expansion 确定。

**成本**：低。
**收益**：A/B 判定的置信度，是后续所有优化可信度的前提。

## 2. P1 — chunk 优化（需重嵌入，逐项验证）

> 核心教训：Stage 1 的表格拆小是负面。以下 chunk 改动都**不是"拆更小"**，而是"修正确性缺陷"
> 或"注入语义"，且每项单独验证，负面即回滚。

### 2.1 公式块低密度（需验证方向，可能负面）

**现状**：`$$...$$` 数学块被原子保护成独立 chunk。采样显示多数公式块其实**紧邻说明文字**
（"$$\Delta...$$ For requirements which are..."），并非纯公式。真正孤立的纯公式块占比待量化。

**先量化**：统计 `content_type` 中"以 `$$` 开头且无字母正文"的 chunk 占比，判断问题严重度。
若占比很小（<2%），则此项降级为 P2。

**若需处理**（方案，需验证）：

- 方向 A：公式块与紧邻说明文字合并成一个 chunk（拆分逻辑小改）。
- 方向 B：公式块嵌入文本注入变量名（类似 path_text，**已证明负面风险高**，不优先）。

**成本**：重切分+重嵌入（68 分钟）+ 评测。
**收益**：待量化；风险中（拆分/注入都可能有 path_text 式的负面影响）。

### 2.2 HTML 表原子保护（✅ 已实施）

**现状**：`_segment_by_atomic_blocks` / `_protect_atomic_blocks` 不保护 HTML `<table>`，
O-RAN 的 214 张 HTML 表可能被 prose 切分切断（36/38 系是 pipe 表，已保护）。

**方案**：原子块检测增加 HTML table（`<table>...</table>` 区间）识别。
**成本**：低（splitter 逻辑）+ 重摄入。
**收益**：小（仅 O-RAN 214 表，占 2%）；但属正确性修复，建议随下次重摄入一并做。

### 2.3 小原子块碎片合并（✅ 已实施）

**现状**：min_chunk=300 合并后仍有 ~5.6% <200 字符碎片（多为小原子块，`_is_atomic_chunk` 保护
不允许合并）。

**方案**：小原子块（<200 字符的小表/小公式）允许与紧邻正文合并。
**成本**：低（`_merge_small_chunks` 逻辑）+ 重摄入。
**收益**：小；但减少孤立低密度 chunk，可与 2.2 一并做。

### 2.4 图片展示（展示而非理解，更正早期误判）

> ⚠️ 更正：早期误判 3GPP 图片是 `.emf` 且信息全丢。实测 **38/36 系图片是 `.jpg`**
> （38 系 2970 张，浏览器可直显），**alt 文字本身就是详细描述**，且 `_clean_markdown` 已
> 保留为 `[图: <描述>]` 存进 chunk。故图片文字信息已在 chunk 里、可被检索，丢的只是 jpg 链接。

**现状**：chunk 文本里是 `[图: Figure X.Y.Z-N: ...]`，jpg 文件路径被删。

**方案（二选一）**：

- **方案 A（重摄入）**：`_clean_markdown` 保留 jpg 链接 → 重摄入（68 分钟，可剥离链接嵌入
  但实践上≈全量）→ 图片目录静态托管 → 前端渲染 `![](url)`。
- **方案 B（不重摄入）**：离线构建 `{Figure 编号/描述 → jpg 路径}` 映射（纯文件扫描，秒级）
  → 图片目录静态托管 → 前端渲染时把 `[图: Figure X-Y-Z: ...]` 反查成图片 URL。

**成本**：低-中（方案 B 不碰 Milvus，仅前端 + 离线映射 + 静态托管）。
**收益**：**用户体验（用户直接看图）**，**不是 Recall**（图片描述已在 chunk，LLM 已能基于描述回答）。
O-RAN 的 106 张 `.emf` 浏览器不显示，量小暂缓或单独转。

**推荐**：方案 B（零重嵌入、快速见效），先验证前端渲染链路，再决定是否值得为"贴图"重摄入。

### 2.5 章节标注缺失（✅ 已修复，Stage 2 首个落地项）

**现状（修复前）**：**31.2% 的 chunk（20,565 个）section_number 和 parent_section_id 都为空**，
主要集中在 RRC（38.331/36.331）与测试规范。

**根因（三层）**：

1. 章节编号带字母后缀（`5.3.5.13b`、`5.7.1a`）→ `SECTION_NUM_RE` 只匹配纯数字。
2. ASN.1 模块标题无编号（`#### NR-RRC-Definitions`）→ 直接父节点 sec_id 空。
3. IE 定义标题用 `#`（level 1，如 `# — *CandidateBeamRS*`）→ 栈式构建按 `#` 层级 pop
   切断了 §6.3 等编号祖先，落到 root。

**修复**（`src/ingestion/splitter.py`）：

1. `SECTION_NUM_RE` 支持字母后缀。
2. `_get_parent_context` 向上查找最近有编号祖先。
3. `_build_section_tree` 无编号标题不按 `#` 层级 pop，吸附到最近编号节点。

**效果（实测）**：

| 指标              | 修复前 | 修复后            |
| ----------------- | ------ | ----------------- |
| 空 section chunk  | 31.2%  | **2.97%**         |
| spec 级 Recall@5  | 0.892  | 0.896（不变略升） |
| spec 级 Recall@10 | 0.942  | 0.963             |

> 章节级 Recall 0.35→0.32 略降，原因是 `test_set.json` 的 `expected_sections` 是粗粒度估计、
> 需校正，而非修复问题（见 P2 待办）。核心收益是 **31% chunk 恢复了章节上下文**，让
> `filter_low_quality`/spec-aware 定向/small-to-big 对这批数据重新生效。

## 3. P2 — 检索微调（边际，低成本）

### 3.1 缩写表扩容

**现状**：`glossary.py` 仅 23 条；3GPP 每篇规范 §3 有数百条。但 LLM query expansion 已覆盖
大部分缩写，且 marked 数据缩写表格式杂乱（TOC 与正文混排），自动提取成本高。

**方案**：手动补充 ~30 个高频 L1/L2 缩写（PRACH/PUCCH/DMRS/SRS/CSI-RS/PTRS/DCI/UCI/TCI/BWP/
CORESET/SSB/PBCH/SR/BSR/PHR/DRX/LCP/SPS/CBG/MCS 等）到 glossary。

**成本**：低（纯数据补充）。
**收益**：边际（LLM 已覆盖），但为 BM25 词法匹配提供确定性补充。

### 3.2 多视角 RRF

**现状**：单查询扩展后检索。参考实现 rel18 用 3-5 个子查询并行 RRF 提升 recall。

**Stage 1 证据**：诊断显示多跳题 expected spec 大多已在候选池（池外缺失少），且 RRF k 扫描
显示 reranker 抹平 RRF 差异。故多视角 RRF 的边际价值存疑。

**方案**：若做，扩展现有 `_taxonomy_decompose_search` 为通用多子查询，仅对"候选池缺 spec"的
查询触发（需先有章节级 Recall 才能准确判定"缺"）。

**成本**：中（代码 + LLM 子查询生成）。
**收益**：待验证，边际风险高。
