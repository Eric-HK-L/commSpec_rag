# 05 — 检索增强技术

## 5.1 技术全景

RAG 系统的检索质量直接决定生成质量。本系统在基础混合检索之上，实现了四层增强：

```
混合检索 (Dense + BM25 + RRF)
    │
    ├── 多跳检索 (Multi-Hop)
    │    查询拆分 → 多轮检索 → 结果融合
    │
    ├── 交叉引用解析 (Cross-Reference)
    │    引用提取 → 定向二次检索 → 上下文补充
    │
    ├── 检索质量评估 (Query Quality)
    │    密度/多样性/覆盖度三维诊断 → 降级策略
    │
    └── 在线搜索补充 (Online Supplement)
         离线不足 → TSpec-LLM + Google CSE 在线补充
```

## 5.2 多跳检索 (`multi_hop.py`)

### 设计动机
复杂查询（如 "5G UE 初始接入时 RRC 和 NAS 层如何协作？"）涉及多个规范、多个协议层，单次检索难以覆盖全部相关上下文。

### 触发条件 (`needs_multi_hop()`)
```python
# 计算检索结果的规范多样性
spec_counts = Counter(r.spec_number for r in results)
diversity = len(spec_counts) / len(results)
# 多样性 < 阈值 (默认 0.3) → 触发多跳
return diversity < 0.3 or len(results) < 3
```

### 多跳流程
```
1. 提取 Top-5 chunk 摘要: build_chunk_summary(results[:5])
2. LLM 分析信息缺口: build_gap_analysis_prompt(query, summaries)
3. 解析缺口 → 子查询列表: parse_gap_response(llm_response)
4. 逐子查询二次检索: for sub_q in sub_queries → retriever.search(sub_q)
5. 合并 + 去重: merge_results(original, supplement)
6. 按原始顺序排列: 保持首轮检索排名优先
```

### 关键设计决策
- **最多 3 个子查询**，控制总延迟
- **去重机制**: 基于 chunk_id 的集合去重
- **失败降级**: LLM 调用失败 → 返回原始结果
- **源标签**: 补充结果的 `_source_tag = "multi_hop"`，便于追溯

## 5.3 交叉引用解析 (`cross_ref.py`)

### 设计动机
3GPP 规范内部有大量交叉引用，如 "see TS 38.413 §8.3.1 for details"。不解析这些引用会导致上下文缺失。

### 引用提取 (`extract_references()`)
正则模式覆盖：
- `TS 38.413 §8.3.1` — 标准引用
- `TR 23.501 clause 5.6.7` — 变体格式
- `3GPP TS 38.413 V17.0.0` — 完整版本号
- `[TS 38.413]` — 方括号引用
- `Annex A.2` — 附录引用

### 处理流程
```
1. 扫描 Top-10 results → extract_references(chunk.text)
2. 去重: _deduplicate_refs(all_refs) — 同一规范同章节合并
3. 限制数量: max_refs=5 (控制延迟)
4. 二次检索: ref.to_search_query() → retriever.search()
5. 合并: 原始结果 + 补充 (去重 by chunk_id)
6. 源标签: _source_tag = "cross_ref", _ref_from = original_ref_text
```

### 特殊处理
- `spec_number = "?"` 的引用被跳过（无法定位）
- 匿名引用 (如 "see clause 8") 保留但不做二次检索
- 二级引用 (A 引用 B, B 引用 C) 不做递归追溯

## 5.4 检索质量评估 (`query_quality.py`)

### 三维评估指标

| 指标 | 计算方法 | 阈值 | 说明 |
|------|----------|------|------|
| Density | 平均分 > 阈值的比例 | ≥ 0.5 | 结果相关性 |
| Diversity | distinct_specs / total_results | ≥ 0.3 | 信息来源广度 |
| Coverage | 有效结果数 / 期望数 | ≥ 3 | 结果充足度 |

### 降级策略 (`diagnose_quality()`)
```
低密度 (Density < 0.3) → 建议: 重写查询 / 使用在线补充
低多样性 (Diversity < 0.3) → 建议: 触发多跳检索
低覆盖 (Coverage < 3) → 建议: 扩展检索范围 / 放松阈值
综合差 (overall_ok=False) → 自动: filter_noise() + 在线补充
```

### 噪声过滤 (`filter_noise()`)
移除低质量 chunks:
- 分数低于动态阈值 (均值 - 1σ)
- 文本长度 < 50 字符的空洞 chunk
- 保留至少 1 条结果 (极端情况兜底)

## 5.5 在线搜索补充 (`online_supplement.py`)

### 架构
```
OnlineSupplement
├── GoogleSearchProvider  (site:3gpp.org)
│    需要: GOOGLE_API_KEY + GOOGLE_CSE_ID
└── TSpecLLMProvider      (tspec-llm.3gpp.org)
     需要: TSPEC_LLM_URL
```

### 触发策略 (`should_supplement()`)
```python
if not self.enabled: return False
if offline_count == 0: return True        # 完全无结果
if offline_best_score < threshold: return True  # 最高分太低
if offline_count < min_count: return True  # 结果太少
return False
```
默认: `threshold=0.6`, `min_count=5`

### 执行优先级
1. TSpec-LLM 优先 (官方来源, 3GPP 原生 RAG)
2. Google CSE 补充 (site:3gpp.org 限定, 剩余槽位)

### 结果格式
```python
@dataclass
class OnlineResult:
    title: str
    snippet: str
    url: str
    source: str     # "google" | "tspec-llm"
    score: float = 1.0
```

格式化注入 Prompt:
```
## 在线补充参考 (外部来源, 非本地规范库)

### 参考 1: PDU Session Establishment
来源: https://...
[snippet content]
```

## 5.6 Spec-Aware 定向检索

### 触发条件
LLM 查询扩展结果中包含 3GPP 规范编号模式 `\b(\d{2}\.\d{3})\b`

### 两阶段处理
1. **定向补充**: 对 hint specs 做 Milvus `filter_expr="spec_number=='38.413'"` 定向检索 (最多 3 个)
2. **分数加权**: 匹配 hint spec 的已有结果 ×2.0 boost

### 执行顺序
精排在前 → Spec-Aware 在后。确保 Cross-Encoder 先提升候选池质量，然后 Spec-Aware 确保目标规范不被稀释。

## 5.7 低质量章节过滤 (`_filter_low_quality`)

自动过滤低信息密度章节:
- **Abbreviations/Definitions/Symbols/References** 章节 (parent_title 匹配)
- **目录/Foreword/Scope** 结构化垃圾文本 (prefix 匹配)
- **Section 1/2/3** 纯 Scope/Refs/Defs 顶层章节

过滤后不足 target_k 条 → 从低质量中补充 (排在末尾)

## 5.8 Chunk 元数据加权 boost (Phase 5 新增)

### 设计动机

3GPP 规范中不同规范号的权威性差异巨大：38.211（物理层核心规范）的回答权重应远高于 38.300（概述性规范）。同时参数表类型的 chunk 对分类列举类问题具有极高信息密度。

### 加权策略 (`_apply_metadata_boost()`)

对分类列举类查询自动触发，按 chunk 的元数据字段加权重新排序：

```
boost = 1.0
if spec_role == "authoritative":  boost *= 1.3   # 38.211~38.423 等物理层/RRC 核心规范
if content_type in ("parameter_table", "definition"):  boost *= 1.2
# 两者可叠加，最大 boost = 1.3 × 1.2 = 1.56
```

### 元数据来源

chunk 元数据在摄入时由 `classify_chunk()` 写入 Milvus scalar 字段：

| 字段 | 值 | 分类规则 |
|------|-----|---------|
| `spec_role` | `authoritative` | 白名单：38.211/212/213/214/321/322/323/331/304/305/413/423 |
| | `overview` | 38.300 (NR 总体描述) |
| | `supporting` | 其他所有规范 |
| `content_type` | `parameter_table` | 含 Markdown pipe/grid table |
| | `definition` | 父标题含 definition/general/principles/overview/architecture |
| | `procedure` | 父标题含 procedure/call flow/message sequence |
| | `overview` | 默认 |

### 效果验证

分类列举类查询（如 "PRACH preamble 有哪些格式"）触发 boost 后：
- 38.211 的 parameter_table chunk 排位大幅提升
- 38.300 的概述性 chunk 自然降权
- 答案准确性和完整性显著改善
