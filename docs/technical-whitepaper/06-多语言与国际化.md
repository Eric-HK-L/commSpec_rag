# 06 — 多语言与国际化

## 6.1 设计目标

3GPP 规范为英文撰写，但全球用户群体涵盖中文、日文、韩文等非英语地区。系统支持：

1. **输入多语言**: 用户可用任意语言提问
2. **英文检索**: 内部始终以英文检索（匹配 3GPP 原文）
3. **输出回译**: 答案翻译回用户源语言

## 6.2 架构

```
用户查询 (任意语言)
    │
    ▼
detect_language(query)
  · 简单启发式: Unicode range + CJK 检测
  · 返回: "zh"/"en"/"ja"/"ko"/...
    │
    ├── en → 直接使用
    │
    └── 非 en → translate_to_english(query, lang, llm)
                  │
                  ▼
                LLM 翻译 Prompt:
                "Translate the following query to English
                 for 3GPP technical document search.
                 Keep technical terms (TS, TR, 3GPP, etc.) as-is.
                 Query: {query}"
                  │
                  ▼
                search_query (英文)
                  │
                  ▼
            [RAG Pipeline: 检索 + 生成]
                  │
                  ▼
                answer (英文)
                  │
                  ├── en → 直接返回
                  │
                  └── 非 en → translate_from_english(answer, lang, llm)
                                │
                                ▼
                              LLM 翻译 Prompt:
                              "Translate the following 3GPP technical
                               answer to {language}. Preserve all
                               specification numbers (TS/TR), section
                               references, and technical terms.
                               Answer: {answer}"
```

## 6.3 语言检测 (`i18n.py`)

### 检测策略
```python
def detect_language(text: str) -> str:
    # CJK Unicode range 检测
    cjk_count = sum(1 for c in text if '\u4e00' <= c <= '\u9fff'
                    or '\u3040' <= c <= '\u309f'   # Hiragana
                    or '\uac00' <= c <= '\ud7af')  # Korean
    if cjk_count / len(text) > 0.3:
        # 进一步区分中日韩 (简化: 默认中文)
        return "zh"
    # 拉丁字符为主 → 英文
    return "en"
```

### 翻译 Prompt 设计
翻译时保留电信专用术语:
```
"Translate the following query to English for 3GPP technical
document search. Keep technical terms (TS, TR, 3GPP, 5G, LTE,
NR, etc.) as-is. Do not translate specification numbers.
Query: {query}"
```

回译时保持技术准确性:
```
"Translate the following 3GPP technical answer to {language}.
Preserve all specification numbers (TS/TR), section references
(§8.3.1), and technical terms (PDU, NAS, RRC, etc.) as-is.
Answer: {answer}"
```

## 6.4 性能考虑

| 阶段 | 额外延迟 | 说明 |
|------|----------|------|
| 语言检测 | < 1ms | 纯 Unicode 范围检查 |
| 翻译 (输入) | 200-500ms | LLM API 调用 |
| 回译 (输出) | 200-500ms | LLM API 调用 |
| **总额外开销** | **400-1000ms** | 仅非英文查询 |

英文查询零额外开销。

## 6.5 容错设计

- 翻译失败 → 使用原始查询 (混合语言检索)
- 回译失败 → 返回英文答案 (大概率可读)
- 检测失败 → 默认 en，不做翻译
- LLM 超时 → 30s 超时 + 降级返回原始文本

## 6.6 局限性

1. **简单语言检测**: 基于 Unicode range，无法精确区分中日韩
2. **翻译质量依赖 LLM**: 对电信术语的翻译质量取决于 LLM 能力
3. **不支持语言偏好持久化**: 每次请求独立检测，无用户语言设置存储
4. **未实现术语词典翻译**: 对于已知术语 (如 PDU→协议数据单元)，未来可加入术语表做确定性翻译
