## 8.2 嵌入缓存 (`embedding_cache.py`)

### 设计目标
在大规模摄入场景中，重复嵌入相同的 chunk 文本是主要性能瓶颈。SQLite 缓存将命中率提升到 ~60-90%（增量摄入场景）。

### 数据库配置
```sql
CREATE TABLE embeddings (
    hash       TEXT PRIMARY KEY,    -- SHA256 完整值
    text_hash  TEXT NOT NULL,       -- 前 16 字符 (辅助索引)
    embedding  BLOB NOT NULL,       -- np.float32 序列化
    dim        INTEGER NOT NULL,    -- 维度校验 (1024)

CREATE INDEX idx_embeddings_text_hash ON embeddings(text_hash);

PRAGMA synchronous=NORMAL;         -- 性能优先
```

## 8.3 Cross-Encoder 精排 (`reranker.py`)

### 动机
Bi-Encoder (BGE-M3) 将 query 和 doc 独立编码后计算余弦相似度，但 Cross-Encoder 将 query-doc 对联合编码，精度更高。在 3GPP 窄域场景下，Cross-Encoder 能更准确判断 "PDU Session" 到底指 NAS 层还是 NGAP 层。

### 融合策略
```python
# Step 1: 归一化原始分数 (RRF 融合后的)
orig_norm = (orig_scores - min) / (max - min)

# Step 2: Cross-Encoder 重新打分
reranked = reranker.rerank(query, results, top_k=len(results))
rerank_norm = (rerank_scores - min) / (max - min)

# Step 3: 加权融合 (保留 RRF 信号)
ALPHA = 0.6
combined = ALPHA * rerank_norm + (1 - ALPHA) * orig_norm
```

**为什么融合而非替换?**
- Cross-Encoder 在窄域 (3GPP) 内判别力有限 — 大部分 chunk 与查询相关度高，分数差异小
- RRF 融合了 Dense+BM25 两路信号，包含关键词匹配和语义相似双重信息
- 融合可保留 RRF 的排序优势，同时用 Cross-Encoder 修正明显不匹配的情况

### 精排模型
`BAAI/bge-reranker-v2-m3` — 与 BGE-M3 同系列，专门针对多语言场景优化:
- 输入: (query, document) 对
- 输出: 相关性分数 [0, 1]
- 候选池大小: `reranker_top_k=100` (从 100 条精选 20 条)

## 8.4 查询缓存

```python
# pipeline.py __init__
self._query_cache: TTLCache = TTLCache(maxsize=256, ttl=3600)

# pipeline.py ask()
cache_key = hashlib.md5(query.lower().strip().encode()).hexdigest()
cached = self._query_cache.get(cache_key)
```
- 相同查询 1 小时内直接返回完整 RAGResponse
- 最大 256 条，LRU 淘汰
- 零开销: hash 计算 < 1ms

## 8.5 批量处理优化

### 摄入批量
| 操作 | 批次大小 | 原因 |
|------|----------|------|
| DOCX 提取 | 逐个 | 单文件耗时 5-30s |
| 分块 | 全量 | 内存操作, 无 IO 瓶颈 |
| 嵌入 (API) | 32 | API 速率限制 |
| 嵌入 (MPS) | 5000/段 | 子进程内存隔离 |
| 入库 | 1000/批 | gRPC 消息大小限制 (64MB) |

### Milvus 优化
- **分区键**: 按 release 分区，增量摄入只重建目标分区索引
- **索引类型**: IVF_FLAT (nlist=1024)，聚类加速 ANN
- **连接池**: 单连接复用，避免频繁建连

## 8.6 路由量化 (预留)
