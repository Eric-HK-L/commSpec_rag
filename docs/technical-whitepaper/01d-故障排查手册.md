# 01d — 故障排查手册

> **目标读者**: 技术人员、开发运维、需要定位系统问题的工程师。
> **原则**: 按 "症状 → 可能原因 → 排查步骤 → 解决方案" 组织，无需阅读源码即可定位问题。

## 1. 排查工具速查

在开始排查前，先掌握这些诊断命令：

```bash
# === 系统层 ===
curl http://localhost:8000/health                          # API 健康检查
curl http://localhost:8000/api/v1/admin/system             # 完整系统信息
curl http://localhost:8000/metrics                         # Prometheus 指标
docker ps -a                                               # 容器状态
docker compose -f deploy/docker-compose.yml logs --tail=50 api  # API 日志

# === 数据层 ===
curl http://localhost:8000/api/v1/admin/stats              # 向量库统计
python -c "from src.config import settings; print(settings)"  # 配置检查

# === 日志 ===
grep -i "error\|exception\|traceback" logs/app.log | tail -30
grep "LLM" logs/app.log | tail -20                         # LLM 调用日志
tail -f logs/app.log                                       # 实时日志
```

## 2. 按症状分类排查

### 2.1 系统无法启动

#### 症状 A: API 启动失败

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| Python 依赖缺失 | `pip list \| grep -E "fastapi\|uvicorn\|pydantic"` | `pip install -r requirements.txt` |
| 端口 8000 被占用 | `lsof -i :8000` | 杀掉占用进程或改 `API_PORT` |
| `.env` 配置错误 | `python -c "from src.config import settings; print(settings)"` | 检查 `.env` 语法，确保无多余空格/引号 |
| Python 版本过低 | `python --version` | 需要 Python 3.11+ |
| Milvus 不可达 | `curl http://localhost:9091/healthz` | 先启动 Milvus |

#### 症状 B: Milvus 启动失败

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| Docker 未运行 | `docker ps` | 启动 Docker Desktop / `systemctl start docker` |
| 端口 19530 被占用 | `lsof -i :19530` | 杀掉占用进程 |
| 磁盘空间不足 | `df -h /var/lib/docker` | 清理 Docker: `docker system prune -a` |
| 内存不足 | `docker stats milvus` | 增加 Docker 内存限制 (Settings > Resources) |
| Volume 权限问题 | `docker compose logs milvus \| grep permission` | `sudo chown -R 1000:1000 /var/lib/docker/volumes/` |

#### 症状 C: 前端启动失败

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| Node.js 版本过低 | `node --version` | 需要 Node.js 18+ |
| npm 依赖未安装 | `cd frontend && ls node_modules/` | `npm install` |
| API 地址错误 | 检查 `frontend/.env.local` | 设置 `NEXT_PUBLIC_API_URL=http://localhost:8000` |
| 端口 3000 被占用 | `lsof -i :3000` | 杀掉占用进程或 `next dev -p 3001` |

### 2.2 检索问题

#### 症状 D: 检索返回空结果

**排查流程图**:
```
检索返回空
  ├─ 向量库中有数据吗？ → curl .../admin/stats → total_chunks == 0?
  │   ├─ 是 → 尚未摄入文档 → 执行 bulk_ingest.py
  │   └─ 否 → 继续排查
  ├─ 查询被正确嵌入了吗？ → 检查嵌入日志
  ├─ Milvus 集合存在吗？ → 检查 collection 名称
  └─ 相似度阈值太高？ → 降低 SIMILARITY_THRESHOLD
```

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 向量库为空 | `curl localhost:8000/api/v1/admin/stats` → `total_chunks: 0` | 执行 `python scripts/bulk_ingest.py` |
| Collection 被误删 | `curl localhost:8000/health` → `milvus: false` | 重新摄入 |
| 相似度阈值过高 | `.env` 中 `SIMILARITY_THRESHOLD=0.95` | 降低到 `0.5-0.7` |
| 嵌入模型未加载 | 日志中出现 `BGE-M3 model not loaded` | 等待模型首次下载完成 (2.2 GB) |
| 查询未扩展 | 极短查询可能无匹配 | 尝试更具体的查询词 |
| 分区过滤错误 | `spec_number` 或 `release` 过滤条件太严格 | 检查 Admin 搜索测试页面过滤条件 |

#### 症状 E: 检索结果相关性差

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 嵌入模型不匹配 | 确认使用的是 BGE-M3 (`settings.embedding_provider`) | 重新摄入（切换模型后必须重新嵌入） |
| RRF 融合参数不当 | 检查 `k` 值（默认 60） | 调整 `src/retriever/search.py` 中 K 值 |
| Cross-Encoder 未启用 | 检查 `RERANKER_ENABLED=true` | 启用精排 |
| 低质量 chunk 未过滤 | 检查 `_filter_low_quality()` 是否生效 | 确认 `query_quality.py` 正常工作 |
| BM25 索引损坏 | 检索结果无 BM25 部分 | 重建 BM25: `rebuild_bm25_from_collection()` |

#### 症状 F: 检索延迟过高 (> 1s)

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| Dense 候选池过大 | `DENSE_TOP_K=200` | 降低到 50-100 |
| Milvus 索引未构建 | Milvus 日志中有 `brute force search` | 等待索引自动构建或手动触发 |
| BM25 索引过大 | `ls -lh data/vectors/bm25_index.pkl` > 5GB | 正常现象，可考虑减少文档 |
| Cross-Encoder 慢 | `RERANKER_DEVICE=cpu` | 设置 `RERANKER_DEVICE=cuda` 或减少 `RERANKER_TOP_K` |
| 磁盘 IO 瓶颈 | `iostat -x 1` 看到高 `await` | 使用 SSD 存储向量数据 |

### 2.3 RAG 问答问题

#### 症状 G: LLM 调用失败

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| API Key 无效 | 日志: `401 Unauthorized` | 检查 `.env` 中 `LLM_API_KEY` |
| API 地址错误 | 日志: `Connection refused` / `Name resolution failed` | 检查 `LLM_BASE_URL`，确认网络可达 |
| 模型名称错误 | 日志: `Model not found` | 检查 `LLM_MODEL` |
| 超时 | 日志: `timeout` / `Read timed out` | 增大 `LLM_TIMEOUT` (默认 60s) |
| 余额不足 | 日志: `insufficient_quota` | 充值或切换 API Key |
| 网络不通（离线环境） | `curl $LLM_BASE_URL/models` 失败 | 部署本地 vLLM/ollama 并修改 `LLM_BASE_URL` |

#### 症状 H: 问答质量差 (幻觉/无关)

**排查流程图**:
```
问答质量差
  ├─ 检索结果准确吗？ → 先用 Admin 搜索测试验证检索质量
  │   ├─ 检索也差 → 回到 §2.2 检索排查
  │   └─ 检索准确 → LLM 问题
  ├─ Prompt 模板合适吗？ → 检查是否注入 Release 上下文
  ├─ Temperature 太高？ → 降低 LLM_TEMPERATURE (默认 0 最佳)
  ├─ Chunk 过长被截断？ → 检查 MAX_CHUNK_BYTES = 55000
  └─ 答案验证开了吗？ → 检查 AnswerVerifier 输出
```

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 检索结果不相关 | 回到 §2.2 检索排查 | 优化检索 |
| Temperature 过高 | `.env` 中 `LLM_TEMPERATURE=1.0` | 设为 `0.0`（确定性输出） |
| Max Token 太小 | `LLM_MAX_TOKENS=256` 截断回答 | 增大到 2048 |
| Prompt 缺少上下文 | 检查 `build_rag_prompt()` 是否正确注入 chunks | 确认 `pipeline.py` Step 4 |
| 答案验证被跳过 | `verifier.py` 报错被静默忽略 | 检查验证日志 |
| i18n 翻译错误 | 非英文查询的翻译/回译出错 | 临时用英文提问验证 |

#### 症状 I: 流式问答 (SSE) 断开

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| LLM 生成超时 | 日志: `LLM timeout` | 增大 `LLM_TIMEOUT` |
| 网络代理断开 | Nginx `proxy_read_timeout` 太短 | 增大到 120s |
| 前端连接中断 | 浏览器控制台有 `EventSource error` | 检查 CORS 配置和网络稳定性 |

### 2.4 文档摄入问题

#### 症状 J: 摄入失败 / 报错

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| DOCX 格式损坏 | 单个文件报 `BadZipFile` / `corrupted` | 重新下载该 DOCX，或删除损坏文件 |
| Pandoc 转换失败 | `extractor.extract_file()` 异常 | Pandoc 对某些复杂格式不兼容，换用其他工具预处理 |
| 文件名解析失败 | 无法从文件名提取 spec_number/release | 手动重命名为标准格式: `TS_XX.XXX_R18.docx` |
| 嵌入内存不足 | `Killed` / `MemoryError` | 设置 `EMBEDDING_DEVICE=cpu` 降低 `batch_size` |
| Milvus 插入失败 | gRPC 消息过大 `RESOURCE_EXHAUSTED` | 降低入库批次大小 (当前 1000) |
| MPS 进程卡死 | Apple Silicon `Metal` 超时 | 设置 `EMBEDDING_DEVICE=cpu` 不用 MPS |

#### 症状 K: 摄入速度过慢

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 嵌入模型在 CPU 上 | `EMBEDDING_DEVICE=cpu` | 如有 GPU 设 `cuda`，Mac 设 `mps` |
| 单个 DOCX 很大 | 某文件耗时 > 60s | 正常现象，超大规范（如 TS 38.300）提取慢 |
| 嵌入缓存太低 | 日志: `cache_hits=0` | 首次摄入无缓存正常，第二次会快 |
| API 嵌入限速 | 使用 OpenAI API 嵌入有 rpm 限制 | 降低 `batch_size` 或切本地 BGE-M3 |

#### 症状 L: 增量摄入跳过了应更新的文档

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 版本号解析错误 | manifest 中 `latest_version` 与文件名不匹配 | 检查 `manifest.py` 的版本解析逻辑 |
| SHA256 相同 | 文件内容实际相同 | 确认是真正新版本 |
| 文件名格式不标准 | 解析出的 version 相同 | 重命名文件或手动清理 manifest 条目 |

### 2.5 嵌入缓存问题

#### 症状 M: 缓存命中率极低

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 首次摄入 | `cache_hits=0` | 正常，第二次摄入会命中 |
| 缓存文件损坏 | `python -c "from src.ingestion.embedding_cache import EmbeddingCache; c=EmbeddingCache(); print(c.stats())"` | 删除 `data/embedding_cache.db` 重建 |
| 文本内容变化 | chunk 文本有微小差异（空格、换行） | 检查分块逻辑是否变化 |
| 数据库路径错误 | `settings.data_abs_dir` 指向错误 | 检查 `.env` 中 `DATA_DIR` |

#### 症状 N: 嵌入缓存文件过大

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 累计多条重复 | 不同规范可能有相同内容的 chunks | 正常现象，SHA256 自动去重 |
| 旧缓存未清理 | 数据库包含已删除文档的嵌入 | `sqlite3 data/embedding_cache.db "SELECT COUNT(*) FROM embeddings"` 查看 |

### 2.6 配置问题

#### 症状 O: 配置不生效

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| `.env` 未被加载 | `python -c "from src.config import settings; print(settings.LLM_MODEL)"` | 确认 `.env` 在项目根目录 |
| 环境变量覆盖 | `env \| grep LLM_MODEL` | 系统环境变量优先于 `.env`，`unset` 后再试 |
| 变量名拼写错误 | `.env.example` 对比 | 严格遵循下划线大写命名 |
| 值类型错误 | `ENABLE_ONLINE_SEARCH=yes`（应为 `true`） | 布尔值用 `true`/`false` (小写) |

### 2.7 多语言 / i18n 问题

#### 症状 P: 非英文查询返回英文答案

| 可能原因 | 排查步骤 | 解决方案 |
|----------|----------|----------|
| 语言检测失败 | 中文被识别为 `en` | 检查 `i18n.py` 的 `detect_language()` |
| 回译失败 | 日志: `translate_from_english failed` | LLM 翻译调用失败，降级返回英文（可接受） |
| 纯英文+数字 | 查询含大量英文术语 | 检测策略偏向英文，可用 `zh` 提示 |

## 4. 日志分析指南

### 4.1 常见日志模式与含义

| 日志内容 | 级别 | 含义 | 应对 |
|----------|------|------|------|
| `📢 Release 变更检测: +2 新增` | WARNING | Release Monitor 发现新文档 | 审核后执行增量摄入 |
| `LLM API call failed, retrying...` | WARNING | LLM 调用正重试 | 观察，3 次失败后会降级 |
| `Reranker disabled, using raw scores` | INFO | 精排模型未加载，使用原始分数 | 检查 reranker 模型是否下载 |
| `Embedding cache miss for N texts` | DEBUG | 嵌入缓存未命中 | 首次摄入正常，高频则检查缓存 |
| `gRPC error: UNAVAILABLE` | ERROR | Milvus 连接断开 | 重启 Milvus |
| `Token limit exceeded, truncating` | WARNING | Prompt 超 LLM 上下文限制 | 减少 `RERANKER_TOP_K` 或 chunk 数 |
| `MPS subprocess timeout` | ERROR | Apple Silicon GPU 嵌入卡死 | 切换到 `EMBEDDING_DEVICE=cpu` |
| `Manifest entry orphan detected` | INFO | 文档文件已删除但 manifest 记录还在 | 正常，自动清理 |
| `Cross-reference resolved: TS 38.413 §8.3.1` | DEBUG | 交叉引用成功解析 | 正常 |
| `Multi-hop triggered: diversity=0.15` | INFO | 多跳检索被触发 | 正常，结果多样性不足 |

### 4.2 日志级别切换

```bash
# 开发/排查时启用 DEBUG 日志
# 方法 1: 环境变量
export LOG_LEVEL=DEBUG
python -m src.main

# 方法 2: 修改 .env
LOG_LEVEL=DEBUG

# 方法 3: 运行时通过 Admin API (如果已实现)
# curl -X POST http://localhost:8000/api/v1/admin/config -d '{"log_level":"DEBUG"}'

# 排查完毕后切回 INFO
LOG_LEVEL=INFO
```

### 4.3 关键日志位置

| 日志文件 | 记录内容 | 排查用途 |
|----------|----------|----------|
| `logs/app.log` | API 请求、LLM 调用、错误堆栈 | 主力排查 |
| `logs/bulk_ingest_v4.log` | 文档摄入全流程 | 摄入问题排查 |
| `stdout` (Docker: `docker logs api`) | 实时输出 | 服务启动问题 |
| Milvus 日志: `docker logs milvus` | 向量库内部日志 | Milvus 故障 |

## 6. 性能问题深度排查

### 6.1 端到端延迟分解

```
用户请求总延迟 = 网络延迟 + API 开销 + 检索延迟 + LLM 生成延迟

排查方法：
1. 使用 Admin 搜索测试页面查看耗时分解（🔍 检索 ms + 🤖 LLM ms + 🎯 精排 ms）
2. 或用 curl + time:
   time curl -X POST http://localhost:8000/api/v1/ask \
     -H 'Content-Type: application/json' \
     -d '{"query":"test","top_k":20}'

各阶段预期延迟：
- 查询缓存: < 1ms (命中)
- 查询扩展: 200-500ms (LLM)
- 查询嵌入: 10-50ms (BGE-M3)
- 混合检索: 50-100ms (Milvus + BM25)
- 交叉引用: +50-200ms (条件触发)
- Cross-Encoder: 100-300ms (100→20)
- LLM 生成: 1-3s
- 总计: 2-5s (无缓存)
```
